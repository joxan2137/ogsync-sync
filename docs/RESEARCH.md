- WARN: run_code relies on `loadstring` + `getfenv` env shadowing, so output capture only catches print/warn/error called from the injected chunk env — output from code that resolves globals differently, from coroutines/other scripts, or async output after the call returns will be missed. - SELF-UPDATE WINDOWS — the canonical rename-old + write-new algorithm, per self-replace's windows.rs: (1) canonicalize `current_exe()`; (2) `MoveFile` the running exe to `<exe>.__relocated__.exe` in the same directory (Windows permits renaming a running image, just not deleting it); (3) call `schedule_self_deletion_on_shutdown` on the relocated file — it copies itself to `<exe>.__selfdelete__.exe`, opens that copy with `FILE_FLAG_DELETE_ON_CLOSE`, and spawns it as a child passing the relocated path; (4) copy the new binary to `<exe>.__temp__.exe`; (5) rename the temp file onto the original exe path. The spawned helper `WaitForSingleObject`s on the parent, deletes the relocated file, then spawns cmd.exe so Windows can release/clean the DELETE_ON_CLOSE handle. https://github.com/mitsuhiko/self-replace/blob/main/src/windows.rs
- SELF-UPDATE WINDOWS — self-replace treats the `.__selfdelete__.exe` filename suffix as a magic trigger: any binary whose path ends in that suffix runs the parent-deletion logic instead of your `main`. If you ship a binary with that name yourself, the logic fires unintentionally. https://docs.rs/self-replace/latest/self_replace/
- SELF-UPDATE UNIX — on Unix the whole problem collapses to `rename()`: the running process keeps its open inode, so atomically renaming the new binary over the old path (same filesystem) is sufficient, and `unlink()` works on a running executable. self-replace's Unix path deletes the filesystem entry immediately; on Windows the delete is deferred until process shutdown. https://lib.rs/crates/self-replace
- SELF-UPDATE — crate API surface: `self_replace::self_replace(new_binary_path)`, `self_delete()`, `self_delete_at(path)`, `self_delete_outside_path(path)` (avoids leaving temp files inside a given dir, e.g. when uninstalling a whole install tree). Documented caveat: if power is cut mid-operation, dot-prefixed temp files with random suffixes can be left behind. https://docs.rs/self-replace/latest/self_replace/
- SELF-UPDATE — `self_update` v0.44.0 is the higher-level layer and re-exports `self_replace` for the actual swap. Backends: GitHub, GitLab, Gitea, S3/GCS/DigitalOcean Spaces. Warnings:
- WARN: The documentation domain rojo.rbx.dev does NOT resolve (DNS ENOTFOUND as of 2026-07-26). Canonical docs live at rojo.space (versioned paths /docs/v7/...). Any code/config referencing rojo.rbx.dev will fail.
- WARN: 7.5.x has NO security hardening on the HTTP server: no Host/Origin header validation (DNS-rebinding exposure for a localhost dev server), /api/open/{id} is not gated to local clients (remote code-adjacent: opens arbitrary tracked script files in the user's editor), and no warning when bound to a network-reachable address. All three were added only in 7.7.0. Do not expose a 7.5.x `rojo serve` beyond loopback.
- WARN: src/change_processor.rs in 7.5.1 uses `fs::write(path, value).unwrap()` for Source writes -- an I/O error (read-only file, locked file, missing dir) panics rather than surfacing a clean error.
- WARN: message_queue.rs in 7.5.1 keeps every message forever in an unbounded Vec with no trimming; long-running sessions with heavy churn leak memory, and cursors are monotonic queue indices (not opaque tokens), so a client that reconnects with a stale cursor will be re-sent the full backlog.
- WARN: The server-side /api/subscribe long poll has NO timeout. Correct client behavior depends on the HTTP client timing out and immediately re-requesting. Rojo's plugin retries with zero backoff on Http.Error.Kind.Timeout, so a server that errors instead of timing out will produce a tight retry loop.
- WARN: Two-way sync in 7.5.x is Source-only and actively buggy: issue #1273 (open, filed 2026-06-03) documents write-while-typing echo loops and the script editor cursor jumping to the bottom. Treat it as unusable for production; do not build a product dependency on it.
- WARN: Do not conflate `syncback` with two-way sync. `rojo syncback` (one-shot place-file -> project extraction, `syncbackRules` project field) is 7.7.0-only and still labelled experimental; it does not exist in 7.5.x at all, not even behind a Cargo feature.
- WARN: Protocol is not forward-compatible: the plugin requires exact protocolVersion equality. 7.5.x = 4 over JSON long-polling; 7.7.0 = 5 over a WebSocket at /api/socket/{cursor} with msgpack binary frames and /api/subscribe removed. Anything you build against the 7.5 protocol breaks on 7.7. (PROTOCOL_VERSION for 7.6.0 specifically was not verified -- 7.6.0 still routes /api/subscribe.)
- WARN: rojo.space/docs/v7/sync-details/ tables list only `.lua` extensions; the 7.5.1 source confirms `.luau` equivalents for every script rule plus `.plugin.lua(u)`. Trust the source over the docs table here.
- WARN: The Roblox creator-docs HttpService.yaml entry for HttpEnabled contains no plugin carve-out text, so the "plugins ignore HttpEnabled" claim rests primarily on the 2020 devforum announcement plus the negative evidence that Rojo's setup docs never tell users to enable HTTP. Treat the exact current-day Studio behavior (especially any localhost special-casing for Marketplace-installed plugins) as not fully verified against a first-party reference page.
- WARN: `rojo plugin install` overwrites a single fixed file (RojoManagedPlugin.rbxm) in the Plugins folder; if the user also installed the Marketplace Rojo 7 plugin they will run two copies simultaneously. Also note the Marketplace copy will trigger a per-domain HTTP permission dialog while the locally installed copy bypasses permissions entirely -- behavior differs by install method.
- WARN: Plugin updates are notification-only via api.github.com/repos/rojo-rbx/rojo/releases?per_page=10 (unauthenticated, subject to GitHub rate limits and corporate blocking; master's Unreleased section adds a fix to disable checks when api.github.com is blocked). There is no auto-update path.

- Bun stdin history: #9041 (hang reading >=16 KiB from stdin via Readable.toWeb(process.stdin), workaround Bun.stdin.stream()) is closed via PR #9580; #3255 (process.stdin / Bun.stdin.stream() never closing on EOF) is closed. Both are directly on the MCP stdio path — large tool payloads and clean exit-on-stdin-close should be regression-tested on the target Bun version.
- Still-open Bun stdio gap: #30831 / #25498 'TODO: stream.Readable stdio' — passing a Node Readable/Writable as child_process stdio is unimplemented. Matters only if your MCP server itself spawns child processes with piped streams.
- bun build --compile cannot include non-statically-analyzable dynamic imports; Deno solved this with --include and an equivalent flag for Bun is still only a request (#11732). Keep all imports static in an MCP server you intend to compile. https://github.com/oven-sh/bun/issues/11732
- Native N-API addons are the main --compile failure class (e.g. DuckDB, #17312). Official guidance: .node files must be imported directly to bundle correctly. Prefer pure-JS deps or Bun built-ins (bun:sqlite) for a compiled MCP server. https://github.com/oven-sh/bun/issues/17312 and https://bun.com/docs/bundler/executables
- macOS distribution requires codesigning or Gatekeeper blocks the binary, and the signature needs JIT entitlements for JavaScriptCore: build, write an entitlements.plist, then codesign --entitlements entitlements.plist -vvvv --deep --sign <identity> ./myapp --force. https://bun.com/docs/guides/runtime/codesign-macos-executable
- Known (dated) friction compiling the v1 SDK with Bun: issue #709 reported 'Could not resolve: @modelcontextprotocol/sdk/server/streamableHttp' and '.../server/mcp' under bun 1.2.17 + SDK 1.13.2 for both bun build --compile and bun run. It was closed as a duplicate of #260, which is actually an unrelated fetch-transport feature request — so the resolution is not documented and current-version behavior is unverified. https://github.com/modelcontextprotocol/typescript-sdk/issues/709
- Testing a compiled stdio server: the official tool is the MCP Inspector, invoked as npx @modelcontextprotocol/inspector <command> (docs show 'node ./build/server.js'; substitute your compiled binary path). https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/stdio.md
- Bun.build() JS API mirrors the CLI: a compile property accepting boolean | target string | CompileBuildOptions object with target, outfile, execArgv and the autoload toggles — usable for a scripted 3-target release build. https://bun.com/docs/bundler/executables

- WARN: Exact v2 API surface should be verified against the installed .d.ts: the repo README shows StdioServerTransport + server.connect(), while docs/serving/stdio.md shows serveStdio(factory). Both appear to exist under './stdio' but the canonical choice and registerTool config keys (description vs title) were extracted from docs by a summarizing model, not read from types.
- WARN: Binary-size figures (62.8 MB darwin-arm64 to 116 MB windows-x64) are a single third-party March 2026 measurement of an unrelated CLI. Your size will differ; expect >50 MB per target regardless, so a 3-target release is ~200-300 MB of artifacts.
- WARN: --bytecode output is tied to the exact Bun version that produced it; pin Bun in CI or startup silently degrades to source parsing.
- WARN: --windows-icon / --windows-hide-console cannot be used while cross-compiling, so a branded .exe needs a Windows CI runner even though the code cross-compiles fine from any host.
- WARN: Anything relying on require.resolve, __dirname-relative reads, or spawning a sibling binary breaks inside $bunfs. Budget for an extract-to-temp step (pattern: Anthropic's extractFromBunfs).
- WARN: Bun fs.watch recursive/Windows behavior has a mixed record of open and closed issues; chokidar-on-Bun-on-Windows inside a compiled binary is confirmed by no source. Test explicitly if ogsync-sync watches files.
- WARN: The MCP-SDK-fails-to-bundle-under-Bun report (#709) is dated (Bun 1.2.17, SDK 1.13.2) and was closed as a duplicate of an unrelated issue, so its fix is undocumented. Single-sourced — validate with a throwaway bun build --compile early.
- WARN: Runtime CLI flags do not reach the embedded Bun runtime except via the BUN_OPTIONS env var or build-time --compile-exec-argv; do not design around passing node-style flags at launch.
